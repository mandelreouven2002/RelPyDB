17. Databases and Backends

Back the same RelPyDB API with a real SQL database — SQLite, PostgreSQL, MySQL, Oracle, Azure SQL or Amazon RDS/Aurora.

The same API, now durable

RelPy() is still a pure in-memory database. Pass a backend and the exact same API — create_table, insert, query, update, delete, joins, group_by — is mirrored to a real SQL database behind the scenes. Nothing about how you write RelPyDB code changes.

backends.py
from relpy import RelPy, AutoNumber, col

db = RelPy()                                   # in-memory (default)
db = RelPy(backend="sqlite", path="data.db")   # local SQLite file
db = RelPy(backend="postgres",
           url="postgresql+psycopg://user:pass@host/db")
How it works. RelPyDB always keeps a full working copy of every table in memory, so the entire query engine runs locally and behaves identically with or without a backend. A backend is a durable mirror: each change is applied in memory first, then written through to the database.

Supported backends

Every SQL backend shares one code path (SQLAlchemy connection URLs), so the backend name or URL scheme is the only thing that changes.

The constructor and the more readable RelPy.connect(...) are equivalent:

connect.py
db = RelPy.connect("mysql",  url="mysql+pymysql://user:pass@localhost:3306/dbname")
db = RelPy.connect("oracle", url="oracle+oracledb://user:pass@localhost:1521/?service_name=FREEPDB1")

A full working example (SQLite)

Define, insert and query exactly as with an in-memory database. When you are done, close() the database (or use it as a context manager).

shop.py
from relpy import RelPy, AutoNumber, col

db = RelPy(backend="sqlite", path="data.db")
db.create_table("users")
db.add_column("users", "id", AutoNumber, is_primary_key=True)
db.add_column("users", "name", str)
db.add_column("users", "age", int, nullable=True)

db.insert("users", {"name": "Ada", "age": 36})
db.insert_many("users", [{"name": "Linus", "age": 54},
                         {"name": "Grace", "age": 85}])
db.update("users", {"age": 37}, where=lambda r: r["name"] == "Ada")

print(db.query("users").where(col("age") > 40).order_by("name").to_list())
db.close()
Output
[{'id': 2, 'name': 'Linus', 'age': 54}, {'id': 3, 'name': 'Grace', 'age': 85}]

Everything written above is now persisted in data.db. Reopen it later and the schema and rows come back.

Installing database drivers

The core library has no required third-party dependencies. SQL backends use SQLAlchemy plus the driver for your database. Install the extra that matches your target:

TargetInstall
Core (in-memory + server + remote)pip install relpy
PostgreSQLpip install "relpy[postgres]"
MySQL / MariaDBpip install "relpy[mysql]"
Oraclepip install "relpy[oracle]"
Azure SQL / SQL Serverpip install "relpy[azure]"
Everythingpip install "relpy[all]"

If a driver is missing, the backend raises a clear BackendNotAvailableError that names exactly what to install.

Connecting to an existing database

Point RelPyDB at a database that already has tables — created by anything — and it reflects the schema and loads the rows, so the full query API works over your real data immediately.

reflect.py
db = RelPy.connect("postgres", url="postgresql+psycopg://user:pass@host/db")

# The schema and data are already loaded:
db.query("customers").where(col("country") == "UK").count()

spend = (
    db.query("invoices")
      .group_by("cust_id")
      .aggregate(total=sum_("total"), n=count())
      .to_list()
)
Reflected integer primary keys come back as plain int columns (you supply the value on insert), not AutoNumber.

Raw SQL escape hatch

When you need to drop to SQL, execute_sql() runs a statement against the backend and returns rows as dictionaries.

raw_sql.py
db.execute_sql("SELECT COUNT(*) AS n FROM users")
Output
[{'n': 2}]

Closing and context managers

Call close() when finished, or let a with block do it for you. flush() is available too, though write-through means data is already mirrored as you go.

context.py
with RelPy(backend="sqlite", path="data.db") as db:
    db.create_table("t")
    db.add_column("t", "id", AutoNumber, is_primary_key=True)
    db.insert("t", {})
# closed and persisted automatically on exit

How write-through works

Because the whole table lives in memory, the mirror is always rebuildable from it, so it stays exactly consistent with zero diffing:

OperationWhat the backend does
insert / insert_manyAppends the new rows (fast path).
updateRebuilds the affected table.
deleteRebuilds materialized tables so cascades stay correct.
DDL (add_column, set_primary_key, create_index)Rebuilds the table structure when it already exists in the backend.

Limitations to know

  • Encryption at rest is logical. Column encryption (is_encrypted=True) protects RelPyDB's own in-memory and JSON storage. Values mirrored to an external SQL backend are stored as their decrypted logical values — leave database-level encryption to the database itself.
  • Reflected integer primary keys are plain int (not AutoNumber) — you provide the id on insert.
  • dict / list columns are stored as JSON. Within a live session they are exact Python objects; after reflecting a fresh connection, JSON-typed columns come back as their JSON text form (lossless by content).
  • The working set is in memory. A table's data should comfortably fit in RAM. RelPyDB is a Python-native relational layer with durability, not a replacement for a production query engine.
