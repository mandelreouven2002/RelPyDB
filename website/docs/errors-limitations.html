21. Common Errors and Limitations

Exception types, what triggers them, and known constraints you should be aware of.

Exception hierarchy

Every named exception below inherits from RelPyError. But not every invalid operation raises one of these — several common mistakes raise Python's built-in ValueError or TypeError instead. The table after this one lists those explicitly, since except RelPyError alone will not catch them.

from relpy import (
    RelPyError,
    SchemaError,
    TableNotFoundError,
    ColumnNotFoundError,
    ConstraintError,
    QueryError,
    QueryTypeError,
    ViewError,
    NoRowsFoundError,
    MultipleRowsFoundError,
    EncryptionError,
)

Error reference — verified RelPyError subclasses

ExceptionTriggered by
TableNotFoundErrorQuerying, inserting into, or calling add_column on a table name that does not exist.
ColumnNotFoundErrorReferencing a column that isn't defined in the schema, in where(), select(), group_by(), join(), pluck(), or an export function.
SchemaErrorIndex name conflicts, a small number of schema-definition rules (for example, an encrypted column also marked as a primary key or foreign key), and corrupted or invalid persistence files.
ConstraintErrorViolating a unique index.
NoRowsFoundErrorCalling .one() when the query returns zero rows.
MultipleRowsFoundErrorCalling .one() when the query returns more than one row.
EncryptionErrorCalling an export with decrypt=True with no key loaded, or loading a persistence file with the wrong encryption key.
ConstraintError is narrower than its name suggests. It is raised only for unique-index violations. Duplicate primary keys, NOT NULL violations, and foreign key violations all raise plain ValueError — see the table below.

Error reference — plain Python exceptions

These are common, expected mistakes, but RelPyDB currently signals them with Python's built-in exception types rather than a RelPyError subclass:

ExceptionTriggered by
ValueErrorDuplicate primary keys; NOT NULL violations; foreign key violations on insert() or a RESTRICT delete; calling update()/delete() with no where and without allow_all=True; updating a primary key or AutoNumber column; calling db.view() / drop_view() / describe_view() with a name that was never registered; most other argument validation.
TypeErrorUsing Python's and / or / not on a Condition instead of & / | / ~; passing a value of the wrong type to a schema or query builder method.

If you want a single block that catches anything RelPyDB can raise for bad input, catch (RelPyError, ValueError, TypeError) rather than relying on RelPyError alone.

Common mistakes and fixes

Using Python and in a condition

❌ Wrong — raises TypeError
db.query("users").where(
    col("age") >= 18 and col("status") == "active"
)
✓ Correct
db.query("users").where(
    (col("age") >= 18) &
    (col("status") == "active")
)

Calling .one() on a query with multiple rows

❌ Wrong — raises MultipleRowsFoundError
user = db.query("users").one()
# Raises if there is more than one user
✓ Correct
user = (
    db.query("users")
      .where(col("id") == 1)
      .one()
)

Deleting all rows without the safety flag

❌ Wrong — raises ValueError
db.delete("users")
✓ Correct
db.delete("users", allow_all=True)

Decrypting without loading a key

❌ Wrong — raises EncryptionError
db = RelPy.load("database.relpy.json")
db.to_list("users", decrypt=True)
# No key loaded!
✓ Correct
db = RelPy.load(
    "database.relpy.json",
    encryption_key=my_key,
)
db.to_list("users", decrypt=True)

Connectivity and server errors

When you use a SQL backend, a remote client, or the server, RelPyDB adds a small family of exceptions. They all inherit from BackendError, which inherits from RelPyError, so except RelPyError still catches every one.

from relpy import (
    BackendError,
    BackendConfigurationError,
    BackendNotAvailableError,
    BackendConnectionError,
    BackendOperationError,
    RemoteError,
    ServerError,
)
ExceptionTriggered by
BackendConfigurationErrorAn unknown backend name, or a missing/invalid url or path (also raised for connect("remote") without a url).
BackendNotAvailableErrorA required library or database driver is not installed. The message names exactly what to pip install.
BackendConnectionErrorThe database or the RelPyDB server cannot be reached.
BackendOperationErrorA backend operation (DDL, DML, reflection or raw SQL) failed.
RemoteErrorA remote server returned an error, or authentication failed (for example a wrong or missing token).
from relpy import RelPy, BackendConnectionError

try:
    db = RelPy(backend="postgres", url="postgresql+psycopg://bad-host/db")
except BackendConnectionError as exc:
    print("Could not connect:", exc)

Known limitations

  • No concurrent writes. RelPyDB is a single-process in-memory object. It is not safe for multi-threaded mutation without external locking.
  • Views are not persisted. Views contain Python callables and cannot be serialised. Re-register them after RelPy.load().
  • No subquery support. Nested queries are not supported in the current query builder. Use views or Python variables to chain results.
  • Performance degrades on very large datasets. The library is optimised for clarity and correctness, not compiled-engine throughput. For >500 000 rows or heavy analytical queries, DuckDB or SQLite will be substantially faster.
  • AutoNumber values can be set manually, with no duplicate protection beyond the primary key check. Passing an explicit value for an AutoNumber column in insert() is accepted silently, and the sequence continues counting up from it afterward. It is only rejected (with a ValueError) if it collides with an existing row's primary key.
  • Primary keys and AutoNumber columns cannot be changed by update(). Including a primary key or AutoNumber column in the values passed to update() raises ValueError; it does not silently ignore the change.
  • Encryption at rest is logical for SQL backends. Encrypted columns protect RelPyDB's own in-memory and JSON storage; values mirrored to an external SQL database are stored as their decrypted logical values.
  • Reflected databases are lossy in two known ways. Reflected integer primary keys come back as plain int (not AutoNumber), and dict/list columns (stored as JSON) come back as JSON text on a freshly reflected connection.
  • A remote client caches a local mirror. Call reload() to see changes made by other clients.

Catching errors gracefully

Foreign key violations raise ValueError, not a RelPyError subclass — so a robust handler needs both:

from relpy import RelPyError, TableNotFoundError

try:
    db.insert("orders", {"user_id": 9999, "amount": 50.0})
except TableNotFoundError as e:
    print(f"Table missing: {e}")
except ValueError as e:
    print(f"Invalid row (e.g. a foreign key violation): {e}")
except RelPyError as e:
    print(f"Other RelPyDB error: {e}")
